# Siliang Engine v0.1.6

v0.1.6 completes the managed no-mmap source path for DeepSeek4 and adds
bounded-prefill attribution. With `--load-mode none`, routed experts, FRONT
tensors, and token embeddings are served from exact model-owned GGUF offsets
instead of being materialized by the ordinary model loader. The default mmap
path is unchanged.

## What changed

- Managed no-mmap routed-expert backing. On Windows, a monolithic expert-major
  GGUF with `--load-mode none`, `--expert-cache`, and a nonzero L2 uses a
  `CPU_SILIANG_MANAGED` proxy for routed expert weights. SiliangEM direct GGUF
  I/O is the only source; the runtime fails closed instead of falling back to
  model-resident bytes.
- DeepSeek4 FRONT from the model file. With `--expert-cache-roll deepseek4`, the
  FRONT roller fills its host store directly from verified GGUF offsets. It no
  longer needs an ordinary host copy of the FRONT tensors.
- DeepSeek4 token embeddings from the model file. Only the requested rows of the
  1,010 MiB F16 table are read per ubatch. This removes the `CUDA_Host` model
  buffer that ordinary no-mmap loading creates for the table.
- Bounded-prefill sweep telemetry. With `--expert-cache-route-stats`, every
  completed prefill sweep emits a `SILIANG_PREFILL_SWEEP` record.
- Prefill ubatch guidance. A three-start A/B on a 7,369-token code prompt
  measured 17.79, 28.65, and 23.84 prompt tok/s median for `-ub 512`, `1024`,
  and `2048`. Use `-ub 1024` with K256 on 8 GB GPUs. A larger ubatch is not
  automatically faster. See
  [`PERFORMANCE.md`](../PERFORMANCE.md#deepseek4-bounded-prefill-ubatch-ab-2026-09-25).

## Qualification

The candidate was `132ff512e`, built locally with CUDA 13.2 for `sm_75`
(`llama-server.exe` SHA-256 `393a88009e86e279...`), on the Windows reference
workstation with the DS4 Flash 0731 expert-major GGUF on NVMe.

- Model-free suite: 71 passing tests with 6 expected failures that document
  known converter limitations. Selected upstream CTest cases: 3/3 passed.
- Strict fork provenance verification passed for the 35-path engine boundary.

Decode correctness used the `runtime-gate.ps1` prompt and request contract
(temperature 0, top-k 1, seed 42, 48 warmup tokens, then 128 tokens) with the
v0.1.3 DS4 profile: K216/R12/P12, 8 GiB LRU L2, FRONT rolling, prefill off,
`-c 4096 -b 512 -ub 512 -t 2 -tb 2`.

| Cell | Output SHA-256 | Decode tok/s | Working set at ready |
| --- | --- | ---: | ---: |
| Cache disabled | `3881836a331d...` | 0.733 | 9.9 GiB |
| L2 only, mmap | `3881836a331d...` | 1.467 | 9.9 GiB |
| L2 only, managed no-mmap | `3881836a331d...` | 1.493 | 3.7 GiB |
| K/R/P + FRONT, mmap, 4 starts | `7f840461ae4c...` (4/4) | 1.892-2.104 | 12.4 GiB |
| K/R/P + FRONT, managed no-mmap | `7f840461ae4c...` | 1.928 | 5.2 GiB |

- The managed no-mmap path is byte-identical to mmap in both profiles.
- L2-only output is byte-identical to the disabled control, so managed L2 and
  direct GGUF I/O do not change results. K/R/P + FRONT diverges from the
  disabled control after about 40 tokens, because experts and FRONT run on the
  GPU. That output is deterministic and coherent.

**Behavior change.** With FRONT rolling enabled, every graph now uses the FRONT
GPU banks. v0.1.5 used them for prompt graphs only when bounded prefill was
enabled; otherwise prompt FRONT ops ran on the CPU. With
`--no-expert-cache-prefill`, greedy output therefore differs from the
pre-v0.1.6 reference `bef55940c`, which has the v0.1.5 FRONT graph rule. It is
deterministic. Prompt processing on the 26-token gate
prompt improved from 1.369 to 1.679 tok/s median. With `--expert-cache-prefill`
the output is unchanged from that reference.

Decode regression versus `bef55940c`, three interleaved starts per build:
candidate 2.033 tok/s median (1.892-2.104), reference 2.131 (2.105-2.159),
-4.6%. This is inside the 5% gate limit. The two builds produce different
tokens, so expert locality differs, and this comparison does not isolate the
runtime.

Bounded prefill, K256/R12/P12, 2 GiB LFU L2, `-ub 1024`, `-tb 12`, on the
7,369-token code prompt from the ubatch A/B:

| Load mode | Prompt tok/s | Working set at ready | Output |
| --- | ---: | ---: | --- |
| mmap | 27.72 | 10.7 GiB | `b332f2378690...` |
| managed no-mmap | 29.76 | 3.5 GiB | `b332f2378690...` |

Both outputs match the `bef55940c`-based A/B build byte for byte. These are
reference-workstation observations, not universal throughput claims.

## Known boundaries

- The Siliang expert arena remains Windows-only.
- Managed no-mmap requires a monolithic expert-major GGUF and a nonzero L2.
  `--check-tensors` is not supported on managed tensors.
- Use `--parallel 1` whenever L1 K/R/P is enabled. L1 K/R/P remains
  incompatible with LoRA.
- Bounded prefill supports at most 256 experts per routed layer.
- `-ub 2048` fits the 8 GB reference GPU but is slower than `-ub 1024`. The
  cause is not yet measured.
- Server context checkpoints split the prompt tail into extra small sweeps.
  `--ctx-checkpoints 0` removes that cost when checkpoints are not needed.
- K and L2 still keep separate residency bookkeeping.
