# Siliang Engine v0.1.3

This experimental release ports the bounded MoE memory hierarchy from the
research branches into the Siliang Engine command line and context lifecycle.

## What changed

- Added typed expert-cache configuration shared by `llama-cli` and
  `llama-server`; every option is visible in each binary's `--help` output.
- Replaced process-environment cache setup with direct `--expert-cache...`
  arguments. There is no compatibility alias or setup helper in v0.1.3.
- Added managed host L2 policies for LRU, LFU, and the custom W-TinyLFU
  W10/SLRU-P80 policy.
- Added a CUDA L1 K policy budget, per-schema R exchange banks, and one bounded
  global pinned elevator P. L1 is valid only when the complete K/R/P mechanism
  is configured.
- Split resident LFU from the research cumulative-LFU admission/bypass policy.
  The latter is selected explicitly with
  `--expert-cache-l1-policy cumulative-lfu` and is not valid for L2.
- Added the architecture-guarded DeepSeek4 FRONT rolling path. General static
  rolling and pre-bake are not part of this release.
- Kept generic schema-based L1 available for manual cross-model bring-up. The
  frozen GPT-OSS gate remains L2-only; DeepSeek4 rolling and prompt-union
  prefill must stay disabled in an unqualified GPT-OSS K/R/P trial.
- Added an experimental, disabled-by-default DeepSeek4 prompt path that forms a
  per-layer expert union for bounded microbatches and reuses K as transient
  residency. Unsupported shapes and
  `min(n_ubatch * top-k, expert-count) > K` fail at startup.
- Kept router scoring and mixture weights on the GPU. The CPU mapper now
  receives only selected expert IDs for cache control and physical-slot
  translation.
- Added four-word, per-layer DS4 route bitmaps with aggregate adjacent-sweep
  coverage/precision and debug-level raw records. The bitmaps are telemetry;
  they do not trigger speculative L2 or L1 admission in v0.1.3.
- Added context-owned state and explicit lifecycle integration for both CLI and
  OpenAI-compatible server use.
- L1 K/R/P is intentionally incompatible with LoRA in this prototype; startup
  and dynamic adapter requests fail closed.
- Added direct commands for the DS4 requalification prototype and conservative Gemma4,
  Qwen3, Qwen3.6, and GPT-OSS trials.

## DeepSeek4 transfer point

The v0.1.3 requalification starts at K216/R12/P12, cumulative-LFU
admission/bypass, serial
decode, 8K context, batch/ubatch 512, and a 12 GiB L2. The operator can select
12, 14, or 16 GiB with `12288`, `14336`, or `16384` MiB.

The source research runtime completed one natural 2,000-token start at each
capacity:

| L2 | Decode throughput |
| ---: | ---: |
| 12 GiB | 2.12587 tok/s |
| 14 GiB | 2.20073 tok/s |
| 16 GiB | 2.28674 tok/s |

These results are real completed observations, but they are not a qualified
v0.1.3 performance claim. The arms were single starts, generated different
token signatures, and used the source research binary. The port needs fresh
output-equivalence, path-armed telemetry, and interleaved multi-start timing.

See [`../CONFIGURATION.md`](../CONFIGURATION.md) for the complete command.

## Experimental prompt path

The prefill mechanism is enabled explicitly with `--expert-cache-prefill` and
uses the existing `--ubatch-size` as its hard bound. For DS4 K216, `-ub 32`
allows at most 192 route choices. P stages the union in bounded waves; R remains
decode-only. L2-to-K admission is exclusive, while P staging and R bypass leave
the L2 copy available. K is invalidated at the prompt/decode boundary. This is a
low-headroom adaptation, not FreeToken-style two-full-layer buffering and not a
general architecture rule.

The route mapper no longer consumes selected mixture weights on the CPU. GPU
top-k selection, normalization, and final expert weighting are unchanged. A
strict 43-layer sweep cursor records 256-bit expert sets and compares completed
mapped sweeps. Startup graph-reservation and optional warmup history are reset
before serving, with a final server reset after capability and slot probes.
Summary output
reports coverage and precision; debug output retains each four-word bitmap,
tags reset/sweep records with a context epoch and monotonic attempt, and reports
a partial terminal sweep as incomplete. This instrumentation does not claim or
enable lookahead.

Before this path was enabled, completed interactive prompts on the 8 GB RTX
2070 workstation measured 1.87 prompt tok/s with `-tb 2` and 4.57 prompt tok/s
with `-tb 12`. They used L2=2 GiB, K216/R12/P12, L2 LFU, the L1
cumulative-LFU admission/bypass policy then spelled `lfu`, FRONT rolling, and
batch/ubatch 512 while the workstation was in normal use. The prompts differed,
so these are observational controls rather than a matched thread-count result.
There is no matched microbatch arm yet, and v0.1.3 makes no prompt-throughput
claim from them.

## Port smoke status

A bounded Windows CUDA smoke exercised both the cache-disabled control and the
current typed DS4 L2/K/R/P/FRONT path. The rendered two-token continuation
matched, all 43 routed layers and the FRONT slab armed, decode uploads and waits
executed, and the relevant failure counters remained zero. Token-limit
completion was observed in the runtime log; a controller disconnect prevented
retention of the CLI wrapper exit code.

The same candidate build then completed `GET /health`, `GET /v1/models`, and a
two-token `POST /v1/chat/completions` request before its owned server process
was stopped. A later one-token streaming request with `--reasoning off` and
`--reasoning-format deepseek` returned clean HTTP 200 content with no PEG parse
error while retaining structured tool parsing. These runs validate current
wiring, length-limited responses, and API reachability only; they are not
throughput or capacity qualification.

This release changes the public `llama_context_params` layout. Applications and
plugins must be rebuilt against the v0.1.3 headers; binary compatibility with a
v0.1.2 library is not claimed.

## Server and Pi

The expert-cache flags work with `llama-server`. Use `--parallel 1` whenever L1
is enabled, then point an OpenAI-compatible client such as Pi at
`http://127.0.0.1:18081/v1`. For a non-reasoning Pi model, also pass
`--reasoning off --reasoning-format deepseek`; this makes a one-token response
return clean content instead of failing on an incomplete reasoning structure,
while retaining tool parsing. Pi 0.84.3 reserves 4,096 tokens when calculating
the output allowance, so a model declared with a 2,048-token context otherwise
sends only `max_tokens: 1`. A model-level `samplingParams.max_tokens` override
can support bounded fresh-session testing, but prompt plus output must still fit
the real server context. The effective server configuration is carried by the
command rather than hidden process state.

## Model boundaries

- Gemma4 and Qwen3 have positive resident-source research observations, but
  their v0.1.3 commands are requalification starting points rather than shipped
  performance presets.
- Qwen3.6 K1440 is a no-go. Its retained three-start GPU-arena observation was
  slower than stock, so the documented v0.1.3 command is the cache-disabled
  control.
- GPT-OSS uses a bounded managed host source. Its prior pinned-staged result is
  diagnostic until this port passes the same correctness and allocation gates.
- M4 is inconclusive and remains a no-go because there is no useful integrated
  architecture implementation to ship.

Whole-L2 CUDA registration, heterogeneous batch-copy experiments, route
replay/oracles as product inputs, DirectStorage rolling, whole-model static
rolling, and pre-bake remain excluded.
