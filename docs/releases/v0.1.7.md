# Siliang Engine v0.1.7

v0.1.7 moves the Siliang engine from upstream llama.cpp `b10270` to `b11188`
(921 upstream commits). It adds no new Siliang feature. It contains the Siliang
changes that the new upstream code requires, and one fix that upstream made
necessary for the managed no-mmap path.

## What changed

- Upstream base `b10270` (`071327508`) to `b11188` (`e85e15cf6`). This brings,
  among others, upstream support for Qwen3.8 Flash Next (`qwen4exp`),
  on-demand reads of large per-layer embedding tables (`--lazy-mode`), a CPU
  panel GEMM for IQ types in prompt processing, and CUDA sparse attention for
  DeepSeek4. The Siliang arena is not yet qualified for `qwen4exp`.
- Managed token-embedding rows no longer reach graph construction as media
  input. Upstream DeepSeek4 now treats `ubatch.embd` as image input and then
  skips hash routing in the first layers. Without this fix, `--load-mode none`
  changed prefill output and decode failed closed.
- The upstream CPU IQ panel GEMM runs only on model-resident expert bytes.
  Experts served by SiliangEM, including managed no-mmap experts, keep the
  existing path.
- Siliang sources are excluded from the new upstream unity build, like other
  core sources. Siliang MoE geometry uses the new per-layer `n_expert_used` API
  and rejects models whose routed layers use different top-k values.
- The fork still runs only Siliang CI and the release publisher; upstream
  workflows stay removed.
- The release publisher now starts when the tag CI run completes
  (`workflow_run`) and publishes that run's verified artifacts. It replaces the
  60-minute polling publisher, which timed out on every tag because tag CI
  takes several hours. v0.1.6 was the first release published this way.

## Qualification

The engine was built locally with CUDA 13.2 for `sm_75` and tested on the
Windows reference workstation with the DS4 Flash 0731 expert-major GGUF on NVMe.
The reference build is the v0.1.6 engine.

- Model-free suite: 72 passing tests with 6 expected failures that document
  known converter limitations. Selected upstream CTest cases: 3/3 passed.
- Strict fork provenance verification passed for the 35-path engine boundary
  on base `b11188`.

Decode used the `runtime-gate.ps1` prompt and request contract (temperature 0,
top-k 1, seed 42, 48 warmup tokens, then 128 tokens) with the v0.1.3 DS4
profile: K216/R12/P12, 8 GiB LRU L2, FRONT rolling, prefill off.

| Cell | Output SHA-256 | Result |
| --- | --- | --- |
| Cache disabled | `0acdf000d4af...` | control |
| L2 only | `0acdf000d4af...` | identical to control |
| K/R/P + FRONT, mmap, 5 starts | `4390be45da14...` | 5/5 identical |
| K/R/P + FRONT, managed no-mmap, 2 starts | `4390be45da14...` | identical to mmap |

Three interleaved starts per build:

| Path | v0.1.6 median | v0.1.7 median |
| --- | ---: | ---: |
| Decode, 128 tokens | 2.014 tok/s (1.942-2.055) | 2.044 tok/s (1.973-2.129) |
| Bounded prefill, K256, `-ub 1024`, 7,369-token code prompt | 28.32 tok/s (27.27-28.91) | 28.66 tok/s (27.47-30.05) |

Both builds produced the same prefill output (`b332f2378690...`). The managed
no-mmap prefill produced the same output at 28.86 tok/s with a 3.5 GiB working
set.

The disabled control shows that greedy decode output changed between v0.1.6 and
v0.1.7 without Siliang involvement. A teacher-forced check fed both builds the
same 25-token continuation of the gate prompt and compared the top-10
next-token distributions. The top token agreed at 24 of 25 positions; the one
difference is the first generated token, where the two leading candidates are
0.20 and 0.18. The median largest probability difference was 0.016 (maximum
0.052). This is one prompt, not a perplexity or KL-divergence campaign.

The managed no-mmap fix was measured on the final engine. The mmap cells above
ran before that fix, which only changes code used by managed token rows; a
repeat mmap run on the final engine produced the same output.

These are reference-workstation observations, not universal throughput claims.

## Known boundaries

- The Siliang expert arena remains Windows-only.
- Greedy output differs from v0.1.6 for the same request, also with the expert
  cache disabled. This comes from upstream numeric changes, not from Siliang.
- `qwen4exp` support comes from upstream and has not been tested with Siliang
  yet. Known arena limits apply: bounded prefill supports at most 256 experts
  per layer, and models with different expert quantization per layer use
  partitioned K.
- Managed no-mmap requires a monolithic expert-major GGUF and a nonzero L2.
- Use `--parallel 1` whenever L1 K/R/P is enabled. L1 K/R/P remains
  incompatible with LoRA.
- `-ub 2048` fits the 8 GB reference GPU but is slower than `-ub 1024`.
